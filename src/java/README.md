# Обработка оптовой заявки на Java

Целевая среда: Eclipse Temurin JDK 21 LTS (Adoptium), сборка обычным `javac`.
Внешних библиотек и доступа к сети не требуется. Также проверено на Oracle JDK
26.0.2.1 с `--release 21`. Python 3.10+ нужен только для сравнительной проверки.

Из папки `src/java` (в ZIP это та же папка):

```sh
java -version
javac -version
mkdir -p out
javac --release 21 -encoding UTF-8 -Xlint:all -d out *.java
java -cp out Main example.json
java -cp out Main example_cancel.json
```

В PowerShell вместо `mkdir -p out` используйте `New-Item -ItemType Directory -Force out`.
Остальные команды одинаковы. Из корня репозитория сначала выполните `cd src/java`.

Первый вход содержит покупателя C1, два стола по 12500.00, одно кресло за
8500.00, остатки 10 и 6 и резерв двух столов по другой заявке. Результат:

```json
{"status":"reserved","request_id":"R1","total":"33500.00"}
```

Второй вход содержит отмену R1 с причиной и три активных резерва: два по R1,
один по R0. Результат:

```json
{"status":"cancelled","request_id":"R1","reason":"Покупатель отказался от заказа","released_reservations":2}
```

Порядок пробелов и переносов JSON не значим. Входные примеры скопированы из
процедурной версии КТ2 без изменения. Полный контракт входа виден в JSON:
идентификаторы и цены — строки, количества — целые JSON-числа, признаки — bool.
Цены неотрицательны, данные каталога и остатков считаются корректными.
Пользовательские количества проверяются отдельно, в том числе bool и 2.0.

## Структура

- `Request` проверяет заявку, объединяет строки и рассчитывает сумму.
- `Customer`, `Product`, `RequestLine`, `Stock`, `Reservation` представляют
  остальные сущности логической модели КТ2.
- `Warehouse` проверяет доступность и меняет состояние резервов целиком.
- `Operation` используется как тип переменной в `Main.process`.
  Через `AbstractOperation` его реализуют `ReserveOperation` и `CancelOperation`.
  Они переопределяют `execute`: одна создаёт резервы, другая снимает их.
- `Main` отделяет JSON от предметных объектов, `Json` читает и записывает JSON.
  Коллекции сущностей — `List` и `Map`; наружу выдаются неизменяемые коллекции.

Связи на UML через `productId`, `customerId`, `requestId` являются логическими
ассоциациями по идентификаторам. Строки принадлежат заявке (композиция), каталог
и резервы передаются складу независимо (агрегация). У отсутствующего остатка
доступное количество принимается равным нулю. Часть загруженных резервов может
относиться к другим заявкам, отсутствующим во входном снимке.

## Проверка

```sh
python3 verify.py
javac --release 21 -encoding UTF-8 -cp out -d out tests/StateTest.java
java -cp out StateTest
```

`verify.py` проверяет 31 сценарий по эталонам процедурной версии из
`tests/cases.json`; если рядом есть `../main.py`, также запускает его для
каждого входа. В ZIP Python-версия КТ2 отсутствует по требованию памятки.
`StateTest` проверяет изменение состояния, повторные операции, отсутствие
частичного резерва, неизменность физического остатка, защиту коллекций и JSON.

Доступность: O(n·m), где n — число объединённых строк, m — число резервов.
Сумма: O(n) арифметических операций и O(1) дополнительной памяти при фиксированной
разрядности сумм. Денежный тип — BigDecimal, округление HALF_EVEN до двух знаков,
как Decimal в КТ2. Цена согласования сравнивается как строка, как в исходной версии.
`agreedTotal` — историческая согласованная сумма; она не обновляется автоматически
при изменении каталога.

Состояние живёт в памяти одного запуска. Нет БД, защиты от конкурирующих
процессов, сохранения результата в исходный JSON или сетевого API.
